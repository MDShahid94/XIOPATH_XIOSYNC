# 06 — Persistence & Schema

> Normative. Defines the single schema authority, migration policy, table
> invariants, indexes, and immutability. Remediates C2, C5, C6, H2, H6, M6, and
> underpins the tenancy guarantees in doc 05. RFC 2119 keywords binding.

---

## 1. Schema authority (C5 remediation)

**INV-SCHEMA-1:** Migrations are the **only** authority over schema. No
application module — not `database.py`, not a repository, not a subsystem like
the old `trust_ledger.py`/`vault.py` — ever issues `CREATE TABLE`, `ALTER`,
`create_all`, or a schema-probe at runtime.

Consequences (each kills a specific XIOPATH pattern):
- No `_init_db()` with `CREATE TABLE IF NOT EXISTS` (kills C5's `database.py`).
- No subsystem-private table creation (kills H9/C5's `phantom/vault.py`,
  `trust_ledger.py` runtime DDL).
- No ORM `metadata.create_all()` anywhere in application code.
- The database a fresh install builds, the one migrations describe, and the one
  tests run against are, by construction, **the same database**.

**INV-SCHEMA-2:** The application, at startup, verifies the DB is at the expected
migration head and **refuses to serve** otherwise (see §3). It never migrates
itself.

---

## 2. Engine & dialect (C6 remediation)

**INV-DB-1:** The control-plane database is **PostgreSQL, single dialect**. There
is no SQLite path, no dual-dialect abstraction, no "works on both." XIOPATH's
core defect C6 — migrations pinned to `sqlite:///data/xiopath.db` while data went
to Postgres — is structurally impossible because SQLite is not a supported
target anywhere in the codebase.

- Local dev, CI, and production all run PostgreSQL (containerized locally/CI).
- Postgres-native features are used deliberately: `uuid`, `jsonb`, partial and
  expression indexes, RLS, `CHECK` constraints, and transactional DDL.

---

## 3. Migration policy (C6 remediation)

**INV-MIG-1:** Migration is a **discrete deploy step**, run **exactly once per
release** against the configured `DATABASE_URL`, **never inside the API process**
and **never per replica**. XIOPATH ran `alembic upgrade head` in the API lifespan
*and* in `start.sh` (C6) — both are forbidden.

Deploy sequence (doc 09 elaborates):
```
1. build image
2. run migration job (single, ordered, against DATABASE_URL)   ← one place
3. gate: assert DB head == release's expected head
4. roll out API replicas (they only READ the head, never apply)
5. API startup check: head matches → serve; else fail fast (INV-SCHEMA-2)
```

- **INV-MIG-2:** One **linear** migration chain. No branching heads. CI rejects
  multiple heads.
- **INV-MIG-3:** Every migration is reversible or explicitly, documentedly
  irreversible; CI runs `upgrade → downgrade → upgrade` on the whole chain
  against an empty database (doc 09/11).
- **INV-MIG-4:** Migrations are **online-safe**: no blocking, unindexed table
  rewrites on large tables without a documented backfill/expand-contract plan.
- **INV-MIG-5:** Destructive migrations (drop column/table) follow
  expand→migrate→contract across releases, never a single-step destroy.

## 4. Universal row invariants

Every table obeys these unless explicitly exempted:

- **`id`**: `uuid` PK, **UUIDv7**, generated by one vetted library in
  `platform/ids` (kills M6's hand-rolled `uuid7()` and `uuid4` fallback). Time-
  sortability is a real, relied-upon guarantee.
- **`organization_id`**: `uuid NOT NULL` FK→`organizations(id)`, **immutable**,
  **indexed**, on every tenant-bearing table (C2). The only exemptions are
  genuinely platform-global rows (doc 03: platform-global capabilities, some
  platform-lifecycle events, the type registry `core.*` namespace), which are
  documented per-table and never writable by tenant APIs.
- **`created_at`**: `timestamptz NOT NULL DEFAULT now()`, immutable.
- **`updated_at`**: `timestamptz` where the row is mutable; absent on
  append-only tables.
- **Immutability** of `IMM` columns (doc 03) is enforced by a `BEFORE UPDATE`
  trigger or a restricted grant, not merely by convention.

**INV-ROW-1:** A tenant-bearing row without a non-null `organization_id` cannot
be inserted (NOT NULL + FK). This is the schema-level root fix for C1/C2.

## 6. Append-only events & versioned memory (H6 remediation)

XIOPATH's `Event` was a normal mutable table despite being called "append-only"
(H6). XIOSYNC enforces it:

- **INV-EVENT-DB-1:** The application DB role has **INSERT and SELECT only** on
  `events` — **no UPDATE, no DELETE grant**. Immutability is a privilege
  boundary, not a code convention.
- **INV-EVENT-DB-2:** For high-assurance streams, each event stores
  `prev_hash` = hash of the previous event in its `(organization_id,
  correlation_id)` partition and `hash` = hash of its own canonicalized content;
  a verifier can detect any insertion/reordering/deletion.
- **INV-EVENT-DB-3:** Retention and redaction are explicit, out-of-band,
  audited operations performed by a privileged migration/maintenance role —
  never by application handlers.
- **Memory** is **versioned, not overwritten**: a change writes a new row with
  `version+1` and sets the prior row's `superseded_by` (INV-MEM-2). Merges
  (doc 07) produce new versions with provenance; originals are retained.

## 7. Indexing & performance

- Every table: index on `organization_id` (the universal filter) and composite
  indexes leading with `organization_id` for hot query paths, e.g.:
  - `events (organization_id, correlation_id, created_at)`
  - `events (organization_id, event_type, created_at)`
  - `operations (organization_id, actor_id, started_at)`
  - `grants (organization_id, actor_id, capability_id) WHERE state = 'active'` (partial)
  - `sessions (auth_identity_id) WHERE state = 'active'` (partial)
  - `tasks (organization_id, state, lease_expires_at)` for lease sweeps
  - `actors (organization_id, actor_type, state)`
- `jsonb` payloads that are queried get GIN indexes; those that are only stored
  do not.
- **INV-IDX-1:** No tenant query relies on a full scan; the org-leading index is
  mandatory. Query plans for hot paths are checked in performance tests (doc 09).

## 8. Type Registry persistence (H3 support)

The Type Registry (doc 03 §8) is **data in tables**, the single authority for
valid type values:

- `type_registry(namespace, category, value, version, state, definition jsonb)`
  where `category` ∈ {`actor_type`, `actor_subtype`, `capability_type`,
  `operation_type`, `edge_type`, `event_type`, `lifecycle_state`}.
- **`core.*`** namespace rows are seeded by migration (the bootstrap sets in
  doc 03) and are the platform baseline; tenant/plugin namespaces are added
  through the registry service, never by ad-hoc constants.
- **INV-TYPE-DB-1:** Writing an entity whose type value is absent (and not
  deprecated-but-allowed) in the registry is rejected at the service layer
  before the row is attempted (doc 03 INV-TYPE-1).
- **INV-TYPE-DB-2:** Code constants exist **only** as migration seed data. No
  runtime read consults a module-level constant set instead of the registry
  (kills H3's competing `ACTOR_TYPES`/`EDGE_TYPES` module constants).

## 9. Repositories & the persistence layer contract

- **INV-REPO-1:** All table access goes through `persistence/` repositories.
  Handlers and services never write raw SQL against tenant tables outside a
  repository. (Lint/architecture rule; doc 04 RULE-ARCH-2/3.)
- **INV-REPO-2:** Every tenant-touching repository method takes `OrgContext` as
  a required first parameter and sets the transaction's `app.current_org` for
  RLS (doc 05 §3.2). No method offers an "all orgs" mode except the audited
  platform-admin repository.
- **INV-REPO-3:** Repositories return domain objects (doc 03), not ORM rows or
  dicts, keeping `domain/` framework-free (doc 04 §2.1).
- Transactions wrap a full use-case; partial writes never leave inconsistent
  state. State transitions that must emit an Operation + Event do so in the same
  transaction (INV-LC-2) so provenance can never be lost after a committed
  change.

## 10. Testing the schema (H2 remediation)

XIOPATH tests fabricated their own tables with `CREATE TABLE IF NOT EXISTS`
(H2), so green tests never proved the migration chain. XIOSYNC forbids this:

- **INV-TEST-SCHEMA-1:** Tests start from an **empty** PostgreSQL database and
  run the **full Alembic chain to head**. Fabricated schemas are banned — there
  is no `conftest.py` `CREATE TABLE`.
- **INV-TEST-SCHEMA-2:** CI runs `upgrade → downgrade → upgrade` over the whole
  chain (INV-MIG-3) and fails on drift between models and migrations
  (autogenerate diff must be empty).
- **INV-TEST-SCHEMA-3:** Cross-tenant negative tests (doc 05/11) run against the
  migrated schema with RLS active, proving isolation on the real database.

---

## 11. Persistence anti-patterns (forbidden)

- Runtime `CREATE TABLE`/`ALTER`/`create_all`/schema probe in app code. **(C5)**
- Any SQLite target or dual-dialect branch. **(C6)**
- Migration inside the API process or per replica. **(C6)**
- A tenant-bearing table/query without immutable `organization_id`. **(C2)**
- An UPDATE/DELETE path on `events` from application code. **(H6)**
- Overwriting memory in place instead of versioning. **(H6)**
- Tests that build their own tables instead of migrating. **(H2)**
- Runtime reliance on module-constant type sets over the registry. **(H3)**
- Hand-rolled UUIDv7 or uuid4 fallback. **(M6)**

Any of these is a persistence regression to be reverted.
